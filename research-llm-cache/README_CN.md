# LLM Prompt Caching: 行业对比与技术分析报告

## 执行摘要

Prompt Caching（提示词缓存/上下文缓存）已从一种小众的性能优化手段演变为大语言模型（LLM）应用的核心经济驱动力。所有主流模型厂商（OpenAI、Anthropic、Google、DeepSeek、阿里巴巴等）均已实现缓存机制，可将输入 Token 成本降低 **50%至90%以上**，并显著降低延迟。

本报告分析了当前前沿模型领域的缓存实现策略及技术要求。

---

## 1. 厂商对比矩阵

| 厂商 | 触发机制 | 核心定价 (读取) | 最小阈值 | 实现方式 |
| :--- | :--- | :--- | :--- | :--- |
| **OpenAI** | 自动 | 50% 折扣 | 1,024 tokens | 零配置前缀匹配 |
| **Anthropic** | 显式 | 90% 折扣 | 1,024+ | `cache_control` 标记 |
| **Google Gemini**| 显式 | 75% - 90% 折扣 | 1,024+ | `CachedContent` 资源 |
| **DeepSeek** | 自动 | 约 90% 折扣 | 64 tokens | 零配置 (V2.5/V3) |
| **Kimi (Moonshot)**| 显式 | 约 80% 折扣 | 1,024 tokens | `context_cache` ID |
| **通义千问 (Qwen)** | 隐式/显式 | 80% - 90% 折扣 | 256 - 1,024 | 自动或 `cache_control` |

## 2. 技术实现细节

具体代码示例和 JSON 结构请参考 [技术实现指南 (英文)](implementation_guide.md)。

### 2.1 前缀匹配（黄金法则）
所有厂商的缓存机制都依赖于**精确前缀匹配**。在 Agent 循环中利用缓存的关键点：
1. **系统提示词 (System Prompt)**：保持完全一致，并置于最顶层。
2. **工具定义 (Tools)**：以固定顺序排列函数定义。
3. **对话历史**：仅追加新消息；切勿对早期消息进行重新排序或重新格式化。
4. **动态数据**：将时间戳、搜索结果或用户特定上下文放在消息数组的最末尾。

### 2.2 显式控制 vs 自动模式
- **自动模式 (OpenAI, DeepSeek)**：无需修改代码。系统会对前缀进行哈希处理并寻找匹配项。
- **显式模式 (Anthropic, Gemini, Kimi)**：需要使用标记或创建专门资源。对于大型上下文，这种方式更稳健。

---

## 3. 智能体 (Agent) 开发最佳实践建议

1.  **避免在系统提示词中包含“当前时间”**：例如在大型系统提示词开头包含 `当前时间: {{time}}`，会导致每次请求都破坏缓存。
2.  **对齐 Token 阈值**：确保你的稳定前缀大于厂商的最小阈值（如 1,024 tokens）以触发折扣。
3.  **保持字节一致性**：即使是 JSON 序列化中的一个额外空格或缩进差异也会导致缓存失效。

---

## 4. 结论

LLM 缓存已分化为两种体验：以 OpenAI/DeepSeek 为代表的**自动模式**（追求易用性）和以 Anthropic/Gemini 为代表的**显式模式**（追求极致优化）。对于生产级应用，Prompt 缓存是维持竞争力的核心技术手段。
